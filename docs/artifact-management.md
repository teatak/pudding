# Pudding 发布产物管理约定

`teatak/pudding` 统一管理 Pudding 的公开发布产物、版本清单和商店展示素材。`pudding-desktop` 负责构建与验收，`teatak.com` 负责官网与宣传工程。本文件是产物归属和归档规则的唯一来源，其他仓库只引用，不维护另一份约定。

本约定从下一次发布开始执行。已经发布的 Windows 0.4.1 保持原状，不补归档、不重新打包，也不改写其发布记录；不要求追溯整理历史产物。

## 仓库职责

| 内容 | 权威位置 |
| --- | --- |
| 公开安装包、更新文件、可选运行资源 | `teatak/pudding` 的 GitHub Releases |
| 已发布构建的来源与文件校验信息 | `teatak/pudding/releases/` |
| 可公开的商店截图、文案、关键词和图片标题 | `teatak/pudding/assets/store/` |
| 通用产品宣传素材、README 图片 | 现有 `teatak/pudding/assets/product/`、`assets/readme/` |
| 构建脚本、打包配置、验收报告、未公开提交包的归档记录 | 私有 `pudding-desktop` |
| 官网代码、网页专用派生图片、宣传动画源码 | `teatak.com` |

品牌图形的原始几何仍由 `pudding-desktop` 维护。官网和公开仓库使用其派生文件或明确标注来源的副本，不改变品牌源码的归属。

## 二进制与版本清单

- DMG、EXE、ZIP、APPX、blockmap 等大文件不提交到 Git。公开下载文件作为 GitHub Release 附件；仅供商店提交的未签名 APPX 留在私有归档，不作为普通用户安装入口。Microsoft Store 用户使用商店链接安装和更新。
- `dist/` 是临时构建输出，不是长期归档。需要保留的未公开二进制存入私有制品存储或备份，并在 desktop 发布记录中记录归档位置、文件名、字节数和 SHA-256；不把完整本机路径或内部访问凭据写入公开仓库。
- 清单必须能定位每个构建的应用版本、渠道、平台、架构、准确 desktop/core 提交，以及文件名、字节数、SHA-256、签名和分发状态。沿用当前发布工具的文件命名，不重命名历史附件。
- 现有 `releases/v<version>.json` 保持原格式和发布范围。如果相同应用版本在其他渠道使用不同源码构建，新增 `releases/<channel>/v<version>.json`，例如 `releases/windows-store/v<version>.json`，记录该渠道的真实来源；不得覆盖原清单，或让 Windows 包借用 Mac 构建的来源。同一构建只维护一份权威清单，其他记录引用它。
- 商店上传包与微软签名后分发的包是不同的文件对象，校验值不能混用。签名、验证、上传、认证和上架状态分别记录，不以“上传成功”代替“已发布”。
- 已发布的标签、二进制附件及其构建清单不可改写。程序内容变化使用新的 beta 或补丁版本；仅调整商店展示素材使用新的素材修订，不要求重新打包。历史授权和许可证记录保持不变。

新增渠道清单是归档规则，不代表现有发布脚本已经自动生成它；归档时必须验证实际文件与记录一致。

## 商店素材归档

按应用版本和素材修订日期保存，例如：

```text
assets/store/v<version>/YYYY-MM-DD/
  README.md
  zh-cn/
    listing.md
    01-conversation-project.png
    02-studio-document.png
    03-studio-start.png
    04-scheduled-tasks.png
  en-us/
    listing.md
    01-conversation-project.png
    02-studio-document.png
    03-studio-start.png
    04-scheduled-tasks.png
```

日期使用新加坡时区，同日多次修订追加 `-2`、`-3`。这是归档布局示例，不表示该修订已经提交或上架。既有 `assets/product/` 和 `assets/readme/` 不做无关的批量迁移。

每个修订的 `README.md` 记录目标商店和产品 ID、对应构建清单、截图实际运行的程序版本/架构和 desktop/core 提交、捕获日期、演示内容说明，以及复用图片的原始来源。截图顺序以数字前缀固定；尺寸和图片 SHA-256 一并记录，便于核对上传文件。

每种语言的 `listing.md` 保存该次使用的完整描述、简短描述、功能、关键词和按文件名对应的图片标题。纯文案修改也新建修订，不覆盖已提交的素材。提交后在归档记录中追加提交 ID、确认日期及当时状态；当前审核与发布状态以 Partner Center 为准。

截图必须来自对应版本的真实产品界面。演示会话、示例文档和模型夹具应明确标注，不展示真实用户数据，也不把后续版本界面当作当前包的界面。

## 官网引用

官网通过正式 GitHub Release、已有下载路由或 Microsoft Store 产品链接提供安装入口，不再维护安装包副本或独立版本清单。商店文案和截图以 `pudding` 的修订归档为准。

网页必须随部署提供图片时，可以在 `teatak.com` 保存压缩、裁剪等派生文件，但要在对应素材说明中记录原始路径、修订和处理方式。宣传动画源码与网页专用设计继续在官网仓库维护；已有下载路由和更新源不因归档整理而更换。

## 公开前检查

从下一次发布开始，提交商店程序包或发布 GitHub Release 前，先完成对应构建清单和商店素材归档，再执行以下检查。

1. 核对二进制校验值、构建来源、平台和架构，确认没有覆盖历史发布内容。
2. 核对中英文文案、截图、标题及实际提交顺序；展示能力与对应构建一致。
3. 排除 API Key、启动 token、证书私钥、真实聊天数据库、个人路径、Partner Center 后台截图和完整测试日志。后台截图与验收证据只留在私有归档，不混入公开商店素材。
4. 更新归档索引和引用，执行 `git diff --check`。发布、商店提交和官网部署各自按对应工作流及授权执行；文件归档不等于批准发布。
